Tag Your Tests: Object/Action FTW

Vilim Hlusicka
 2025-10-28  603 words   3 minutes 
Contents

Sometimes the simplest additions make the biggest difference. While working on test specifications, I realized that many test cases describe what happens but not where it happens. To fix that, I started adding a small column, or a quick tag, that turned out to be a subtle but powerful way to bring structure and instant clarity to my test documentation.

I am the author of test specifications for few products, with one of them which I am continuously maintaining, and designing another one for the product currently in development. During the process of both designing and maintaining I confronted the challenge which might seem a bit trivial - until it starts to go on your nerves. I think you might find yourself in this, so lean in and try to visualize it.

You are scrolling through the test specification and trying to figure out which test cases refer to CRUD processes of a user. You have to read the title of every test case, so you better hope the titles are short and self explanatory. Even then it is challenging to distinguish the exact purpose of every test cas, but imagine when you have to do it lots of times, when time is the essence, when you are already lacking the concentration. It gets annoying, you know it. So why not help yourself to quickly distinguish test cases?

I present to you: The Object/Action!

Wait, what? The Object/Action, and it’s so simple and efficient that you’ll just slightly laugh when you figure it out. Let me explain it more and this time without exaggeration. The idea is to describe what object on a test case you are working on and what is the action you are using on it. Two words are enough to define it.

Here are some examples with the test case description:

  • Test case goes through creation of a new user -> the object/action will state User / Create.
  • Test case goes through editing an existing user -> the object/action will state User / Edit.
  • Test case goes through validations for creating a new user -> the object/validation will state User / Validations.

Mind you that nothing is limited to only having to having only one column or field withing the test specification reserved for this. This is just an example of how I personally use it, but let it be just an outline for your solution.

OVDJE UBACITI NEKE PRIMJERE SA SCREENSHOTOVIMA. MOŽE JEDAN TEST CASE, A MOŽE I VIŠE NJIH.

I hope you realize how simple and effective it is meant to be. Fast scroll through your test specification in Excel or TestRail and it let’s you figure out which action the specific test cases does to which object. This is best to be used on a regression tests which can be comprehensive by it’s nature.

I personally use it by creating the additional column which I name Action / Object and then for every test case define it by writing as mentioned in previous examples. It depends whether you’re using Excel to manage your test specification or one of test management tools. In Excel you can just create an additional column, but also test management tools such as Testrail support adding custom fields/columns so no unpleasant surprises are supposed to be there.
